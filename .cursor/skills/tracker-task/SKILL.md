# Задача из трекера

Ключ задачи бери из сообщения (DENT-284, STO-170). Если ключа нет — спроси до создания ветки и коммита. Коммит и пуш не делай, пока пользователь явно не попросит. Навыки tracker-review и tracker-commit-pr сам не вызывай: сначала задай вопрос и дождись ответа.

## 1. Ветка от свежего develop

Префикс:

- `feat` — новый функционал
- `issue` — баг или блокер
- `fix` — доработка после тестов

Формат: `<префикс>/<КЛЮЧ>-<номер>`. Пример: `issue/DENT-284`.

Не используй `bug/` и имя без ключа трекера.

```bash
git fetch origin develop
git checkout -b issue/DENT-284 origin/develop
```

Подставь префикс и ключ. Если ветка уже есть — переключись на неё. Если в рабочем дереве есть чужие незакоммиченные изменения — остановись и спроси.

## 2. Разбор

До кода разбери задачу, макет (если есть ссылка или файл), текст инструкции и API. Сверь их между собой.

Фронтенд: проверь, что функционал из задачи опирается на существующий или описанный API. Выпиши, какие запросы, поля и ошибки нужны экрану. Если бэкенд этого не отдаёт или контракт расходится с макетом, запиши расхождение и не додумывай поведение.

Бэкенд: сверь ТЗ с текущей архитектурой. Зафиксируй, где живёт логика, какие контракты и ошибки уже есть и что изменится у существующих клиентов. Макет не подменяет API.

## 3. План

Напиши план реализации. Отдельным списком выпиши уточняющие вопросы, блокеры и расхождения между задачей, макетом и API.

Если без ответа нельзя сделать поведение правильно — остановись и жди. Если путь однозначный, кратко зафиксируй план и переходи к реализации.

## 4. Реализация

Делай по пунктам плана. Не расширяй задачу соседними правками.

## 5. Ревью

Проверь diff сам, как лид. Не запускай Bugbot и не используй навык review-bugbot.

После реализации остановись и спроси: «Начать проверку навыком tracker-review?»

Не вызывай tracker-review, пока пользователь явно не согласится. Коммит и пуш не делай.

Фронтенд: корректность сценария, регрессии, краевые случаи, соответствие макету и стиль кодовой базы. Проверь, что весь функционал из задачи работает относительно бэкенда: нужные запросы уходят, ответы и ошибки разбираются, заявленный сценарий не остаётся только вёрсткой. Найденное исправь до проверки в браузере.

Бэкенд: качество кода, соответствие ТЗ, архитектуре и контракту API, регрессии и краевые случаи. Браузер не открывай.

## 6. Проверка в браузере

Для бэкенда этот шаг пропусти.

Для фронтенда проверь изменённый сценарий через уже подключённый Playwright MCP (user-playwright). Сначала прочитай схему инструментов, потом открой страницу и пройди каждый заявленный в задаче сценарий. Данные бери из задачи, окружения или тестовых хелперов проекта. Сверь экран с макетом и убедись, что функционал работает вместе с бэкендом, а не только отображается.

Не устанавливай Playwright и не запускай npx playwright install или npm install playwright. Если данных для входа нет — спроси, не выдумывай учётные данные.    


## 7. Отчет 

Отчёт отправь и остановись. Спроси: «Проверка закончена. Продолжить навыком tracker-commit-pr?»

Не вызывай tracker-commit-pr, пока пользователь явно не согласится. Коммит и пуш не делай.
